# 架构

## 三层职责

**Adapter** 把平台事件翻译成会话请求。Discord 这边处理消息、附件、线程、斜杠命令；QQ 走 OneBot 协议。适配器不做业务判断，只负责协议转换和回执。

**Supervisor** 是信任根。它管理进程生命周期，维护会话表与任务表，做任务路由，执行审批策略，写事件日志，跑计划任务，暴露管理 API。所有需要「裁决」的动作都收在这一层。

**Engine** 执行具体任务。构造上下文，调用模型，处理工具调用循环，跑 Hook，读写记忆，做上下文压缩，最后产出结果。Engine 不决定自己有没有权限，权限由 Supervisor 给。

拆成三层的原因是可替换。换平台不用动推理逻辑，换模型不用动平台协议，改策略不用发版。

## 一次请求的路径

1. Adapter 收到消息，解析出平台、频道、用户、附件
2. 转成会话请求，提交给 Supervisor
3. Supervisor 查会话，建任务，检查策略，投递给 Engine
4. Engine 加载节点配置，拼上下文，调模型
5. 模型返回工具调用时，Engine 执行工具，把结果塞回对话，继续推理
6. 推理结束，结果交给 output 节点处理
7. Supervisor 落事件、更新任务状态，Adapter 把结果发回平台

## 进程模型

Supervisor 是常驻主进程，Engine 按 worker 数起协程池，Adapter 按平台各起一个。进程挂了由 Supervisor 拉起，状态从任务表恢复。

配置里 `max_workers` 控制并发任务数，默认 4。任务之间共享进程但不共享上下文，隔离靠 session。

## 事件流

每次状态变化写一条事件：任务创建、开始、工具调用、审批请求、审批结果、完成、失败。事件按 task_id 聚合，可以回放整条执行链。

事件日志是排障的主要依据。线上出问题时，先看事件流判断卡在模型、工具还是审批。

## Provider 层

统一的模型接口，按名字解析到具体实现。目前覆盖 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、Gemini 这几种协议。

新增后端一般只需要加一个 Provider 文件，实现约定的方法，注册进 Registry。调用方拿到的永远是同一种消息结构和同一种返回结构。

## 配置分层

- `config/runtime.yaml`：运行时参数，可以进仓库
- `data/config.yaml`：含敏感值的配置，不进仓库
- `.env`：凭据，不进仓库
- `config/nodes/*.yaml`：节点定义

这个分层是为了让「能公开的」和「不能公开的」在物理上分开。开源仓库里只有第一类和第四类的示例。
