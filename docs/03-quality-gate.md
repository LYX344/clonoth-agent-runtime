# 输出质量门禁

## 问题

把风格要求写进 system prompt，只能提高概率，不能保证结果。模型会漏，会在长对话里漂移，也会在被指出问题后换个说法继续犯。

对长期运行的服务来说，输出质量需要一层确定性检查。

## 做法

在生成节点和用户之间插入一个 `script` 类型的节点。生成节点把结果交给它，它做检查，通过就放行，不通过就退回。

```yaml
id: quality_gate
type: script
name: 输出质检
output: __source__
script: |
    # 检查逻辑
    ...
script_timeout_sec: 10.0
```

在生成节点一侧只需要一行：

```yaml
output: quality_gate
```

## 检查项

**词表**。维护一份禁用词表，命中的词直接判不合格。词表按类别分开，便于单独调整。

**句式**。正则匹配固定套路，例如「不是 A，而是 B」这类先否定再肯定的结构、语气加形容词的搭配、破折号密度过高。

**乱码与错误回显**。检测连续异常字节、替换字符、堆栈信息、内部错误前缀。这类内容一旦漏到用户侧，比文风问题严重得多。

**长度**。消息平台有硬上限，超长会被直接截断，用户看到的是残缺内容。检查器先按分隔符切段，超限的段再按句子边界二次切分，尽量保证语义完整。

## 退回机制

不通过时返回 reject，并附带两样东西：问题清单，原文。问题清单要具体到「哪一类、哪几个、出现在哪」，这样生成节点能定向修改，不用从头重写。

提示里明确要求不许用同义词替换绕过检查。这条约束很关键，否则模型会把「删除」理解成「换个说法」。

超长但没有其他问题时，检查器直接自动重分段并放行，不打断生成流程。

## 为什么放在脚本里

- 确定性：同样的输入永远得到同样的判定
- 可测试：检查逻辑是纯函数，可以单独写单测
- 可迭代：改词表不用改提示词，不用重新调模型
- 零成本：不消耗 token，不增加推理延迟

代价是维护成本。词表会越来越长，规则会互相冲突，需要定期清理。这部分工作没法自动化。
